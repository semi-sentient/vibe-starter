# TODO — pre-launch checklist

Work remaining before tagging the template as ready for public use. Items are grouped by how they get verified. (The per-_project_ go-live gate for a builder shipping their own app lives in `DEPLOY.md` → "Ready for real users?"; this file is the template maintainer's release checklist.)

## Must do before release

- [ ] **Run the contact-form tutorial end-to-end with a real agent.** The first-feature walkthrough in `README.md` is prose + code the builder writes — it is never type-checked or linted in this repo, so it can rot. Before release, have an agent follow it from a clean checkout (add `CONTACT_EMAIL`, write the route + Resend wrapper, mount it, exercise valid/honeypot/`400`/`429`) and fix any drift from the real `rateLimit()` / Resend / zod APIs.
- [x] **Cross-platform smoke tests (P16).** The Tier-1 local-only runbook now lives in [`CONTRIBUTING.md`](CONTRIBUTING.md) → "Local verification" (clone → `bootstrap.sh` → `docker compose up -d` → `npm install` → `npm run dev` → sign up via the console code → `npm test` → `lint`/`typecheck`/`build` → a local commit). The CI OS matrix is the automated gate ([`.github/workflows/ci.yml`](.github/workflows/ci.yml) → the `cross-platform` job runs install/typecheck/lint/build on macOS, Linux, and Windows; the DB-backed `test` leg stays Linux-only). Verified on macOS this session; Linux/Windows are covered by the CI matrix (3-OS green is observable once the branch is pushed) plus a human run of the runbook. The five pre-listed risks are each fixed-or-documented in `CONTRIBUTING.md` → "Cross-platform risks": CRLF/line endings is fixed portably via [`.gitattributes`](.gitattributes); the Windows `CLAUDE.md` symlink, gitleaks presence, `bootstrap.sh` shell support, and the `:5432` port conflict are documented caveats.
- [ ] **Reconcile `skills-lock.json`.** Confirm the lock lists the 9 skills (the 7-skill PRD pipeline + `handoff` + `prototype`), that every entry has a real (non-placeholder) hash, and that `.agents/skills/` on disk matches the lock.
- [ ] **Apply the GitHub settings with `npm run setup:github`.** It installs **two** rulesets on the default branch and turns on auto-delete-merged-branches plus auto-merge. `main-protection` refuses deletion and force-pushes with **no bypass for anyone** — history loss is what a revert cannot undo. `main-required-checks` requires `Build & test`, `Secret scan` and `Docker smoke`, **with a bypass for the admin repository role** — that is what lets `npm run release` push its version-bump commit and tag straight to `main`; enforcement for the agent lives in the agent contract (`docs/agents/shipping.md`), and the ruleset is the accident backstop. It needs **admin** access on the repo, and refuses outright without it rather than half-applying. The old "run it only after CI has been green once" caution should no longer apply: an admin — which whoever runs this always is — is offered the bypass on the checks ruleset, so making `Docker smoke` required should not be able to strand the PR that introduces it. Worth confirming rather than assuming, though — the bypass was measured against a **direct push**, not against a PR merge whose required checks never ran. Two things to confirm afterwards rather than assume: that `gh api /repos/{owner}/{repo}/rulesets` actually lists both rulesets (rulesets are a **paid feature on private repos**, so a skip line and exit 0 does not mean they were installed), and that a PR is genuinely blocked while a check is red — judge that from a **non-admin** view, since an admin is offered the bypass. (Also noted in `DEPLOY.md`.)

## Verify on real accounts (the builder's go-live journey; see `DEPLOY.md`)

These need external accounts, so they're maintainer dry-runs rather than CI gates.

- [ ] **Walk `DEPLOY.md` on fresh accounts.** Stand up a throwaway Railway project + Postgres, a fresh Resend account (incl. **verifying a sending domain** and confirming mail reaches a non-account address), and a Stripe account (test→live keys + the live webhook), following the runbook verbatim. Note any step that's stale or surprising.
- [ ] **Cut the first real release with `npm run release`.** Land a couple of conventional commits on `main`, then run it and confirm the whole chain: the new `## [X.Y.Z] - YYYY-MM-DD` section is prepended to `CHANGELOG.md` **without duplicating the header block**, `package.json` + `package-lock.json` are bumped, the `chore(release): vX.Y.Z` commit stages **only** those three files (it never sweeps up an unrelated dirty file), the **annotated** `vX.Y.Z` tag and the commit reach the remote together via `git push --atomic --follow-tags` — `--atomic` so a refused branch update cannot leave an orphaned tag behind, annotated because `--follow-tags` ignores lightweight tags — and `gh release create` publishes the same notes. On a repo with no `vX.Y.Z` tag yet the first release seeds at `v0.1.0` rather than bumping. The push and the `gh release create` are the only parts of the flow never exercised offline. Also confirm the refusals read sensibly to a non-technical user — a chore/Dependabot-only window legitimately refuses, and that is the intended policy.
- [ ] **(Optional) Railway live deploy dry-run (P16 Tier-2).** From a fresh clone: live Stripe-CLI webhook forwarding, push a PR to watch CI go green, and a real Railway deploy. **Never required to ship the template** — purely a confidence pass on the documented go-live path.

## Notes

- `CHANGELOG.md` is written by `npm run release` (git-cliff, from conventional commits) — don't hand-edit it; just verify it cuts correctly (above). Its header block, everything above the first `## ` heading, **is** `cliff.toml`'s `[changelog] header` byte-for-byte; editing one without the other duplicates the header on the next release. `CHANGELOG.md` is Prettier-ignored for the same reason.
